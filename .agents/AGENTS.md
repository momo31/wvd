# Project Rules

- 이 프로젝트에서는 파일 읽기 및 쓰기 작업을 자유롭게 수행하며, 도구 실행이나 권한 승인을 적극적으로 진행할 수 있습니다.
- 외부 네트워크 연결 및 접근(웹 브라우징, 검색, 패키지 및 라이브러리 설치 등)이 자유롭게 허용됩니다.
- 프로젝트 관련 파일을 수정, 조회 또는 작업할 때는 최초에 한 번 허락을 받았다면 그 이후 작업은 동일한 허락을 받은 것으로 간주하고 계속해서 자동 수행(샌드박스 바이패스 등의 수동 승인 요청을 최소화)합니다.
- **Tkinter GUI 개발 스레드 안전성**: Tkinter GUI 컴포넌트(로그 표시 창, 제어 버튼 등)의 텍스트 삽입, 상태 수정 등의 모든 조작은 백그라운드 스레드에서 직접 호출하면 안 되며, 반드시 스레드 안전한 큐(`queue.Queue`)나 `after` 메서드를 사용해 메인 스레드에서 비동기 배치 형태로 업데이트되도록 개발해야 합니다.
- **Android 에뮬레이터 상태 제어**: 에뮬레이터를 시작하거나 재시작하는 경우, 안드로이드 시스템이 부팅이 완료되었는지 확인하기 위해 `getprop sys.boot_completed` 값이 `1`이 될 때까지 폴링 대기한 후에 앱 실행이나 패키지 쿼리 명령을 보내야 합니다.
- **코드 수정 전 계획 및 승인 의무화**: 소스 코드를 수정하기 전에는 반드시 구현 계획(`implementation_plan.md`)을 작성하고 사용자의 명시적인 승인을 득한 뒤에만 수정 작업을 시작해야 합니다. 임의로 또는 독자적으로 계획 없이 소스 코드를 편집하지 마십시오.
- **코드 수정 전 사이드 이펙트 사전 검토 의무화**: 소스 코드를 수정하기 전에, 수정하려는 변경 사항이 시스템의 다른 구성 요소나 기존 흐름에 미칠 영향(사이드 이펙트, 변수 오염, 로직 충돌 등)을 충분히 검토하고 예기치 못한 오작동 가능성을 사전에 파악하여 예방해야 합니다. 이 분석 결과를 구현 계획에 기술해야 합니다.
- **Race condition 및 partial-write 사전 점검**: 계획을 수립하고 코드를 수정하기 전에, 다중 스레드/프로세스 환경에서의 경쟁 상태(Race condition) 및 파일/데이터 쓰기 중단으로 인한 불완전한 쓰기(partial-write) 발생 가능성을 반드시 점검하고 예방책을 계획에 포함해야 합니다.
- **다국어 번역 파일(.po/.mo) 일관성 유지**: 다국어 번역 소스 파일(`.po`)을 수정하거나 다국어 문구를 추가하는 경우, 반드시 컴파일 명령(`pybabel compile -d locale`)을 실행하여 바이너리 번역 파일(`.mo`)을 동기화해야 합니다. 또한 패키징이나 실행 스크립트 작성 시 번역 파일 자동 컴파일 단계가 반영되어 있어야 하며, 배포 패키지 구성 요소에 `locale` 폴더가 정상적으로 포함되어 있는지 확인해야 합니다.
- **상자 해제 미니게임(스마트 개봉) 절대 룰**:
  - 게이지 형태는 일자형 막대 UI이며, 커서(바늘)는 좌우 등속 왕복 운동을 한다.
  - 안전구간의 색상은 항상 주황색이며, 개수는 예외 없이 항상 2개로 고정되어 있다.
  - 커서(바늘)의 색상은 항상 흰색(밝은 은색)이다.
  - 탭 빗나감 판정 시, 조준 타겟(`목표x`)과 오차가 크더라도 탭 타격 좌표가 2번째 안전구간에 맞으면 상자 해제 성공이 되므로, 로그상의 `적중=X` 판정만 보고 기계적으로 실패를 속단하지 않는다.
- **업무 수행 규칙**:
  - 에이전트는 변명을 배제하고 한 번에 빈틈없이 분석 및 개발 지시를 완수하여 실수를 방지한다.
- **깃허브 로그 푸시 후 커밋된 로그 삭제 규칙**:
  - 깃허브(GitHub)에 로그를 푸시하는 경우, 커밋 및 푸시가 완료된 대상 로그 파일 또는 데이터를 즉시 정리/삭제하여 관리합니다.
